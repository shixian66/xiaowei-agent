## 1. 目的、适用范围与成功标准

形成长期共用的开发方式，覆盖需求分析、功能、Capability、Web/API/CLI、修复、重构、配置、依赖、数据库迁移、测试、文档与发布，不限定 W2 或任何单个里程碑。

所有任务共用生命周期；计划深度、验证范围和人工决策随风险变化。阶段权限、确定性安全链和独立审查继续由现有规范约束。

成功标准是：任务范围与基线明确；第一条可运行路径尽早获得反馈；审查能发现实际缺陷；重复状态维护减少；证据可复用且不外推；已授权范围内连续推进；每个交付物可独立接受或拒绝。不存在能一次证明“永远最佳”的流程，本版是完整基线，后续修改须有故障或交付数据支持。

## 2. 角色、授权与停止条件

| 角色 | 负责 | 交付 |
| --- | --- | --- |
| 用户 / 项目负责人 | 目标、优先级、产品取舍、权限与风险接受、里程碑开工、合并或发布授权、验收归档 | 可追溯的决定；已有有效授权直接引用 |
| Claude / 指定实现者 | 调查、方案、实现、测试、根因修复、证据与交接整理 | 可运行且范围明确的交付物 |
| Codex / 指定独立审查者 | 按精确 SHA 核对真实 diff、调用链、测试有效性与证据上限 | 阻断项、非阻断建议、未覆盖范围 |

用户可以明确调整分工。实现者自检不能冒充独立审查；需要独立审查不意味着自动引入多 Agent 或新框架。

- 已批准目标内的代码定位、只读调查、常规实现选择、回归修复和本地可回退工作连续推进，不逐函数、逐文件、逐测试重复申请许可。
- 复杂任务按现有里程碑门完成设计、计划评审和开工确认。已有规格直接引用，不为同一决定重写一份 PRD、规格、计划和 Context Pack。
- 新增产品范围、改变已批准契约/权限、真实服务接入、读取真实凭据、部署、不可逆数据操作或改变已接受风险时，只暂停受影响动作，提交具体差异与证据；其他已授权工作继续。
- 用户限定“只读入职/只读审查”时严格只读。离线实现授权不自动包含联网、真实目标或部署；能够运行命令也不等于拥有业务授权。
- 普通信息缺口能由源码或已有决定回答时先查证；不能判断且影响正确性时一次列清必要问题。缺信息、缺环境、缺授权分别记录，不能互相代替。
- 不自行合并、部署、归档；复用有效授权时核对对象、范围和条件，不能把上一轮授权套到不同目标。

## 3. 一套生命周期，三档工作深度

统一顺序：确认目标和事实 → 确定风险与验收路径 → 完成必要设计/计划 → 最小实现与早期运行 → 相关及最终验证 → 独立审查与修复 → 获授权集成/发布 → 更新当前状态。

只读咨询或审查在交付判断和证据后结束，不为了套流程创建分支、实现计划或产品测试。缺环境的探索可输出有边界的结论；临时探针不能直接算正式实现。

| 档位 | 典型触发 | 设计与计划 | 验证与审查 |
| --- | --- | --- | --- |
| 轻档 | 不改变行为的拼写、链接、纯机械调整；能证明影响局部 | 在任务或 PR 中说明目标、文件范围、验证方式 | 相关检查与真实 diff；无需另建规格或重型运行环境 |
| 中档 | 复用既有契约的功能、普通修复、UI/入口行为、常规能力扩展 | 在现有计划或 PR 中说明调用链、验收场景、失败分支；按可验收结果切片 | TDD、相关契约/eval/入口路径；收尾按项目基线运行全量与静态检查，精确 SHA 独立审查 |
| 深档 | 鉴权、租户/目标、审批、SQL/查询边界、持久化迁移、并发恢复、凭据/网络权限、公共契约、部署拓扑或安全门变更 | 先明确不变量、授权、兼容/迁移、失败与恢复；按现有规则评审详细计划，触发架构决策时处理 ADR | 全量、相关安全/集成/eval、关键保护反证、精确 SHA 与真实调用链深审；运行/部署仍需对应证据 |

分类按影响与失败后果，不按文件数量或后缀。修改授权文档不能因只改 Markdown 就算轻档；只读能力也可能触及敏感读取、跨目标或资源预算而升级。

现有硬门优先：触及 `governance/`、`planning/` 或 `tools/` 的任何变更都运行完整 security gate；ADR、里程碑及 CI 的既有要求不因本表被豁免。发现范围或风险扩大时更新评估，不为维持原档位隐藏变化。

## 4. 开工：最小必要上下文与可执行的验收

新任务按 `AGENTS.md → ARCHITECTURE.md → AGENT_HANDOFF.md → README.md → DEVELOPMENT_PLAN.md` 入职，随后读取相关源码、调用方、测试及 ADR。记录实际目录、分支、HEAD、远端基线、未提交/未跟踪变化；旧仓库、旧会话和摘要只作线索。

同一任务继续时，先核对 HEAD、工作树与新消息；已读文档未变化则复用，发生变化才读取相应 diff 和受影响依赖。切换任务、里程碑、基线或授权时重新核对对应真源。减少重复阅读不等于跳过首次入职，也不等于忽略工作树改动。

每个交付物只需要一份任务说明，写在已有计划或 PR；尚无这些载体时先写在任务消息中：

```text
目标与完成条件：谁在什么入口完成什么；哪些情况必须拒绝或降级。
基线与范围：精确 SHA、已有未提交变化、本轮范围及不做的事。
现有实现与落点：真实调用链、要复用的接口、相关决策链接。
风险与权限：档位、不能破坏的边界、已有授权及缺失条件。
验收与恢复：实际命令/入口、成功与失败场景、环境、回退或安全恢复方式。
切片与下一步：依赖顺序、每片可验收结果、当前阻塞及责任人。
```

普通局部修改可以用几句话完成这六项，不需要六个标题。复杂任务的详细计划只展开当前获准阶段；设计写决策和取舍，实施计划写落点、顺序和验证，不逐段复制。

计划必须尽早确定运行环境是否可用、是否获授权。缺 Docker、数据库、浏览器或真实目标条件时明确缺哪种证据及由谁补齐；不能到收尾才发现退出标准无法执行，也不能借此调用未授权服务。

## 5. 实现：一个结果、一个根因、尽早跑通

1. 从批准的最新基线建立隔离分支；遵守现有 `claude/<topic>` 约定或用户明确指定。保留其他人的改动，不以清理工作区为由丢弃文件。
2. 行为变更先写会因目标问题失败的测试，核对失败原因，再写最小实现。集合导入失败或夹具异常不能冒充目标行为已被测试。
3. 优先复用现有组件和标准库；以当前用例为边界，不预建没有消费者的字段、通用工厂、框架或配置项。
4. 在必要契约与存储前置成立后，尽早形成一条从正式入口到可观察结果的路径。该路径应有一个成功对照和一个重要失败场景；后续补齐批准的边界矩阵。
5. 同类缺陷沿共同根因检查所有相关调用方及对称路径；不只在评审评论的那一行加补丁，也不顺带重构无关模块。
6. 在可验证、可回退的节点提交检查点。一个 PR 承载一个根因或可独立接受的交付物；依赖性的契约/迁移前置可以单独交付，不强求每个底层 PR 都有 UI。

任务拆分以结果和依赖为依据，不以“每个文件一个任务”或固定行数为目标。调查或验证已经证明设计不成立时，先更新事实与方案，再继续实现；不反复要求模型重写相同代码碰碰运气。

普通 Capability 默认复用既有运行、治理与 DTO，新增自己的参数、确定性计划、证据、渲染和测试。显式登记属于装配成本；只有测得重复成本并设计好快照/权限边界，才另行评估自动发现或更通用的声明机制。不得为了“零内核修改”而把新安全语义藏在领域代码中。

## 6. 验证：按实际边界选择证据

| 变更类型 | 最早要验证的真实边界 | 不能替代它的材料 |
| --- | --- | --- |
| Web/UI | 正式启动入口、页面引用的资源、浏览器实际可取得的 Cookie/token、成功操作、关键拒绝；视觉变化在浏览器检查 | 直接调用内部 helper、仅 ASGI 通过、截图本身 |
| API/CLI/进程 | 正式 HTTP/命令/启动入口、参数与错误码、退出码、取消或故障结果 | 只调内部服务方法 |
| Capability | 正式 Runtime 链上的参数/目标、Planner、Admission、fake adapter、Evidence、Render、相关 eval | 只测 planner 输出、模型回答看起来合理 |
| 数据库/并发 | 正式 migration、真实隔离数据库、事务/约束/回读、需要时的独立并发连接与故障注入 | 内存 fake、只检查 DDL 字符串 |
| 外部 SDK/服务 | 离线 adapter 契约先行；获准后取得对应版本与环境的真实调用和失败证据 | SDK stub、mock、静态配置通过 |
| 配置/部署 | 实际进程装配、挂载/配置来源、固定版本启动、健康与 ready、回读和获准的恢复步骤 | Compose 静态渲染、镜像构建或单元测试通过 |
| 文档/纯机械变更 | 与规范和代码一致、链接有效、相关文档契约、真实 diff | 为凑数量新增与风险无关的运行测试 |

正式路径可以连接 fake provider 或隔离环境，但必须说明替身覆盖到哪一层。浏览器运行、隔离数据库、真实外部服务和生产部署各自独立标记，不能互相冒充。

### 快速循环与最终门

- 实现中运行能定位本轮变化的相关测试；中/深档收尾再执行最终门。不要在输入完全未变时无理由反复运行相同重型检查。
- 四条权威命令继续以 [ADR-008](../../adr/ADR-008-engineering-and-test-baseline.md) 为准：`python -m pytest -q`、`python -m pytest -m security -q`、`ruff check .`、`mypy src`。不增加平行命令真源，也不在本次优化中关闭 CI job。
- 关键安全修复做正向对照、目标反例和必要的隔离变异：删除对应保护后目标测试必须能察觉。确认加载的是变异副本，避免因错误 import 或较早的其他拒绝而假绿。
- 测试必须观察对外行为或不变量。不要把无关 token/SQL/错误字符串出现在文件里当作行为证明；语义本来就是精确字节匹配的契约仍须精确断言。
- 不为无行为文本或简单机械改动制造测试框架。既有测试发现当前范围外失败时，记录复现和基线差异，判断其是否影响交付；不得直接归为“历史问题”或修改测试掩盖。

### 证据复用的条件

每份证据至少绑定 SHA、命令、环境/依赖、结果和未覆盖边界。相同输入的有效结果可引用，不能声称本轮重新执行。源码、相关配置、依赖、数据库版本或被验证环境变化后，按影响重新验证；最终候选 SHA 所需的门不能靠旧分支结果补齐。

独立审查仍复核测试的充分性与可信度；已归档边界没有新变化或失败证据时，不重复打开整个历史里程碑。遇到新风险，应说明新增证据和具体受影响范围。

## 7. 审查、集成与交付

实现者送审一次提供：base/head SHA、目标与实际 diff、测试及运行证据、已知限制。审查者第一轮按真实调用链系统检查，不以 PR 描述或已有评论替代 diff。

每条问题写清：位置、触发条件、实际行为、影响、证据、期望行为。阻断项须来自当前代码/契约、可复现失败或必需退出条件的缺失；没有当前证据的理论担忧和风格偏好列为非阻断建议。没有实际执行的结论标注“只读推理”。

修复按根因闭合并补相关回归。复审聚焦变化与影响范围，不机械重做整轮审查；基线漂移、公共契约或安全链变化时扩大范围并解释原因。既不承诺一轮查尽所有缺陷，也不设“达到两轮就必须放行”的上限。

交付前同时确认：批准范围完成、必需验证有证据、阻断项已解决、文档口径对应、回退或安全恢复条件明确。随后按有效授权执行合并、部署和验收；这些状态分别记录，不从前一个自动推导后一个。

交付说明沿用四段：已验证、只读推理、未覆盖、残余风险。简单任务可精简为四句。部署证据绑定实际 SHA/镜像、运行命令、环境、健康检查与签认时间；无法安全降级时记录前向恢复方案，不能虚构“可回滚”。用户验收与归档继续需要明确签认。

## 8. 文档与上下文：每种事实只有一个维护位置

| 载体 | 唯一职责 | 何时更新 |
| --- | --- | --- |
| `AGENTS.md` | 稳定协作规则、任务分档、授权与验证纪律 | 协作规则变化；不记录每日 PR 状态 |
| `ARCHITECTURE.md` / ADR | 模块责任、接口与安全语义、决策及变更门 | 真正改变架构/契约/权限/状态语义时；不复制阶段进度 |
| `DEVELOPMENT_PLAN.md` | 产品路线、阶段依赖、交付物与退出标准 | 路线或门变化；不逐能力追加流水 |
| `README.md` | 定位、导航和当前可执行的安装/启动方法 | 启动和使用方式变化；阶段进度指向 handoff |
| `AGENT_HANDOFF.md` | 当前基线、有效授权、正在做什么、未解决风险/阻塞、下一步、证据入口 | 相关事实变化时做增量更新 |
| 已有设计/实施计划 | 本轮独有的决策、落点、顺序、验收场景 | 该任务范围或设计变化；引用稳定真源 |
| `docs/CAPABILITIES.md` | 从 Registry 生成的能力地图 | 声明变化后生成，不手工编辑 |
| 既有归档/验收报告 | 已关闭里程碑的证据、复盘与历史授权来源 | 经明确验收后归档；当前文档保留链接 |

handoff 不以固定 KB 限额驱动删减。先核对每条风险是否仍有效，再移出已经关闭的过程记录；未解决风险、批准来源和证据缺口必须保留。Git 能记录修改历史，但不能替代没有写入任何地方的运行与签认记录。

文档守卫按保护对象取舍：能力声明/生成内容一致、阶段归属、授权边界和错误宣称等有价值；纯粹固定叙述句式的守卫可在确认用途后简化。先消除重复事实或提供等价保护，再删旧断言；不得批量删掉整个文档测试文件来“降低成本”。

通用 skill 是执行辅助。项目规则和用户明确指令优先；不通过改插件缓存绕过流程，不让多个 skill 为同一已批准动作重复建立批准门。若确有尚未满足的硬门，指出具体来源、原文和影响，完成所有可独立推进的工作后再请求该决定。

## 9. 最少量的复盘与流程演进

在现有 PR 或验收报告增加三项即可，不建设新的统计平台：

1. **首次可运行结果用时**：任务开工到第一个正式路径结果；注明环境和替身。等待用户、授权或环境的时间单列，不混成编码耗时。
2. **复审返工根因数**：按独立根因计数，并注明输入/契约/实现/测试/环境等来源，避免按评论数量制造虚假比较。
3. **后期首次暴露的问题数**：原可在局部入口、集成或安全测试发现，却直到整体验收/部署/用户使用才暴露的问题。

未采集就写“未采集”，不估算补填。流程生效后适用于所有任务，连续几个可比交付物用于评估效果；不是只给某个里程碑试用。没有量化时间数据时，可以确认具体缺陷被前移发现，但不能宣布整体提速几倍。

只有重复故障、真实维护成本或新需求证明不足时，才调整规则或评估代码生成、插件化、更多并行执行、框架及新的基础设施。每次优化写清要减少哪种工作、保留什么验收证据；不以新增工具数量作为成熟度。

## 10. 通用性检查

| 场景 | 按本流程应如何处理 |
| --- | --- |
| 改一处 README 拼写 | 轻档，查实际 diff/链接，不新建规格、运行数据库或改 handoff 状态 |
| 修改页面显示并修会话失效跳转 | 显示部分按影响验证；会话路径按鉴权风险评估，走浏览器正反例 |
| 新增复用既有契约的只读能力 | 中档起评，专属实现/登记/相关 eval；涉及规划/工具仍过全量安全门 |
| 新增跨目标查询或不同审批语义 | 先按深档处理契约与授权，不借“只读”或 manifest 绕过决策 |
| 新增数据库表/约束 | 迁移、真实隔离数据库、兼容与恢复；纯 fake 不代替这些证据 |
| 修复生产事件 | 先按现有授权保留证据并控制影响；紧急操作受运行授权约束，事后补根因和回归，不借紧急状态自动清理现场 |
| 修改依赖或 Compose 配置 | 判断实际调用和启动影响；读取官方版本信息，执行对应兼容/运行检查，不只比较文本 |
| 仅做架构咨询或精确 SHA 审查 | 输出事实、判断和边界；没有变更请求就不实施 |
| 验证需要未授权的真实服务 | 保持该动作未执行，推进独立离线工作；不伪造更高证据，也不无限等待 |
| 已通过评审后基线或范围变化 | 显示变化、评估失效证据、补对应检查；旧批准不自动覆盖新范围 |

## 11. 一次落地到现有规则的范围

采用一个目的明确的流程文档变更完成全项目接入，不把 W2 作为适用边界，不穿插产品实现。以下是获批后的落地顺序；不是本文件已经完成的修改。

1. **更新 `AGENTS.md` 的既有章节**：收进角色/授权粒度、三档流程、最小任务说明、正式路径前置、验证复用、审查与收尾规则。替换对应旧段落，保留安全边界、代码落点、四门和 secret 纪律；不整份附加本文。
2. **同步文档责任与引用**：`DEVELOPMENT_PLAN.md` 保留里程碑进入/退出与批准门，日常执行细则引用 AGENTS；README 保留运行说明，进度指向 handoff；ARCHITECTURE 保留稳定语义，把阶段流水移交 handoff/归档。
3. **整理 handoff**：逐条核对当前事实与风险，移出已闭合过程、修复冲突，保留有效批准来源、未覆盖证据与下一步。搬移内容保留可追溯路径，不把未知风险当作已解决。
4. **调整受影响的文档守卫**：检查 `tests/contract/test_doc_fact_binding.py` 等实际依赖。对改为引用的事实验证真源与引用关系；保留有效的授权、阶段归属和证据等级保护，不为每条新措辞新增字符串断言。
5. **验证并精确审查**：检查真实 diff、相对链接、文档冲突、归档前后事实覆盖和相关测试；若触及产品源码或 CI 行为则超出本次纯流程范围，另行评估。既有 CI 门继续运行，不通过优化流程降低 gate。
6. **确认生效**：负责人批准修订后由获授权人员集成；handoff 只记录规则版本/提交、影响与未完成事项。新任务使用新规则，进行中的已批准计划继续有效；变更其范围或硬门需要相应明确决定。

### 落地验收清单

- 三档路径均有明确进入条件、完成条件和升级触发，不把小改动做成完整架构项目。
- Web、API/CLI、能力、迁移、配置、外部接入和发布均能找到自己的验证路径。
- 已批准范围内无需重复逐步许可，真实调用、部署、权限和破坏性操作的独立门仍明确。
- 当前状态只在 handoff 维护；规范、启动方法、路线和历史证据各有出处。
- 原有风险、批准来源和证据链接搬移后可追溯，没有通过删文档降低约束。
- 四条权威命令、强制 security gate、独立精确 SHA 审查、显式验收归档保持成立。
- 不新增工作流平台、并行状态文件、个人全局规则或无实际需要的工具依赖。
- 交付说明区分“设计已交付”“规则已生效”和“提效已测量”；缺哪项就明确缺哪项。
