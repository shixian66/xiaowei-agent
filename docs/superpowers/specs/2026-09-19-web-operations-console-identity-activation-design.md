## 1. 大白话结论

小维 Web 不再被设计成“所有人都来逛的门户”，而是分成三个清楚的入口：

1. **运维任务工作台**：给 Admin 和运维人员使用，用于和小维对话、发起任务、查看任务状态与安全证据；
2. **Admin 管理中心**：只给 Admin 使用，用于维护用户、权限名单和数据库、Prometheus、AI API、飞书等运行参数；
3. **单个结果详情页**：普通用户只通过一条具体结果链接进入，不提供首页、任务台、“我的结果”或配置入口。
   M7 已有的群任务只读详情仍可由当前群成员通过具体链接打开，但它同样不是普通用户门户。

用户不再手工找飞书 `user_id/open_id`。第一次通过飞书登录时，系统自动取得飞书身份；若还没有绑定，
就创建“待激活申请”，由小维通知 Admin，Admin 明确同意后才建立身份和角色。连接测试与用户登录彻底分开：
Admin 测试飞书回调只验证应用配置和 OAuth 回调，不要求用户已经在身份名单中，也不会创建用户 Session。

数据库结果边界保持不变：**真实结果行、预览和导出只允许申请人及该次申请的审批人**。Admin 能管理账号、
配置和审计，但不能仅凭 Admin 角色绕过某一条数据库结果的访问控制。链接不是权限，激活也不是结果授权。

部署目标是“安装后已经完成的功能都能正常用”，不是继续藏在开发阶段开关后面；但认证、权限、数据库结果
边界、`ToolGateway`、SQL/策略/审批链、Secret 与内部端口等安全底线全部保留。

## 2. 已确认的产品决策

### 2.1 用户和入口

- 产品层只展示三个角色：`ADMIN`、`OPERATOR`（运维人员）、`USER`（普通用户）。
- Admin 是最高管理角色；系统初始化固定创建 `admin/admin`，第一次登录强制修改密码。
- 项目负责人明确接受“首次改密前可能暴露默认口令”的风险，本设计不改成随机初始密码或安装令牌。
- Web 的主要用户是 Admin 和运维人员。
- 普通用户不提供工作台、任务列表、Admin 配置和“我的结果”；新增产品能力只允许通过具体结果链接进入
  单页详情，既有群任务只读链接继续按群成员 ACL 工作。
- 手机端只保证单个结果页和单任务只读详情可读，不建设手机版运维工作台、任务发起、任务列表或后台配置。

### 2.2 身份激活

- 飞书 OAuth 自动取得飞书身份，不要求管理员或用户手工填写 `user_id/open_id`。
- 未登记身份必须进入待激活流程，不能自动成为普通用户、运维人员或 Admin。
- 小维可以向 Admin 发起激活确认；Admin 必须明确同意或拒绝，系统不能自己决定。
- 群内触发时，小维可以在群内用不含敏感正文的通用卡片提醒可识别的 Admin；没有可 @ 的 Admin 时，
  仍进入 Admin 管理中心待办，并走可用的私聊通知。
- 结果链接触发时只显示“身份待激活”，不在群里披露结果主题、SQL、结果行或结果是否存在。
- 激活完成后，群内用户重新提交原请求；系统不自动执行激活前的原始任务。结果链接可以刷新或重新打开。

### 2.3 权限和数据库结果

- DBA、值班人员、查询人、审批人不是第四到第七个全局角色，而是资源或流程范围内的名单/职责。
- 群成员可查看该群任务的完整**安全证据摘要**和“还有更多证据”提示；数据库真实结果行不进入群卡片。
- 数据库结果预览与导出继续只允许该次查询的申请人和审批人。
- Admin 可查看任务与私聊审计内容；每次查看必须留审计记录。该能力不扩展到无关数据库结果行。
- Admin 可以发起自己的任务。未来受控写能力若允许 Admin 自审，必须由明确的 `ApprovalGate` 策略实现，
  不能由前端按钮绕过审批链；本文不开放 E1，也不授予任何真实写操作。

### 2.4 配置和部署

- Admin 页面维护人能理解的参数：环境、名称、地址、端口、账号、Secret、数据库名、TLS 等；
  “逻辑资源 ID、generation、digest、identity fingerprint”等只放高级诊断，不作为主表单。
- Admin 配置中心允许维护数据库、Prometheus、AI API、飞书和用户/职责名单。
- 配置中心只维护受控参数，不编辑 capability、Planner、SQL 模板、Policy、审批算法或工具调用顺序。
- 产品部署中，已实现的服务应启动并可在配置完成后使用；不以历史里程碑开关永久隐藏功能。
- “全部功能正常使用”不等于放开认证、权限、真实结果、Secret、网络和执行安全边界。

## 3. 当前基线事实与问题根因

以下是 `origin/main@475573c` 的源码事实，不是对目标状态的声称：

1. 当前 `/app` 未登录时返回一段内联的极简 HTML，只有标题、密码框和按钮；`app.css` 没有完整登录页
   设计，所以页面看起来像浏览器默认表单。根因不是主题颜色，而是登录页没有独立产品壳。
2. 当前本地管理员只有一个账号，页面甚至不显示用户名输入；源码已实现 `admin/admin` 和强制首次改密。
3. 当前飞书 OAuth **连接测试已经不查询身份目录、不会签发 Session**。如果页面让人感觉必须填用户 ID，
   是测试、登录和身份管理在信息架构上没有被讲清楚，不应重写正确的连接测试语义。
4. 正式飞书登录在 OAuth 换到 `open_id` 后立即查询静态身份目录；查不到就返回通用认证失败。当前缺的不是
   “怎么取得 ID”，而是持久化待激活申请、Admin 审批和审批后的身份绑定。
5. 当前身份目录是静态 JSON，使用 `operator/dba/oncall/viewer/approver/admin` 六个标签；这与面向用户的
   三角色产品模型不一致，也不支持 Web 上管理用户。
6. 当前存在两个容易混淆的“Admin”：本地 `LOCAL_ADMIN` 能配置系统；飞书 `admin` 只取得任务权限，不能
   配置系统。目标设计必须把“产品角色”和“认证来源”分开，消除这组歧义。
7. 当前 `/app` 把任务列表、AI 输入区、当前任务和集成配置塞在同一个页面，`app.js` 同时承载任务轮询、
   提交和配置逻辑；它能工作，但继续叠加用户管理、资源配置和结果页会形成单页巨石。
8. 当前运维工作台在低于 1280px 时整体隐藏。目标仍不做手机运维台，但应支持常见的 1024/1100px
   笔记本和分屏场景；手机只保留只读详情与具体结果页。
9. 当前配置中心只有 Gemini 和飞书，没有数据库、Prometheus、AI Provider 通用参数和用户职责维护。
10. 当前仓库有安全任务详情页，但没有“数据库真实结果预览/导出”的现成 Web 子系统。本设计只能定义其
    新边界和接入 Port，不能把安全任务详情假装成数据库结果页。

## 4. 方案比较

### 方案 A：继续把所有内容塞进 `/app`

按角色用 CSS/JavaScript 隐藏模块，在现有 `index.html + app.js` 中加入激活、用户、资源和结果逻辑。

- 优点：短期文件少；
- 缺点：隐藏不是授权，普通用户仍可能下载运维台代码；登录、任务、配置、结果彼此耦合；页面和测试会快速
  失控；
- 结论：拒绝。

### 方案 B：同一模块化单体中的多壳层设计（推荐）

保留一个代码仓库和既有窄进程装配，但把认证、运维工作台、Admin 管理中心和结果页拆成独立 HTML/JS
壳层；后端通过共享 application 服务和类型化 DTO 协作。

- 优点：复用现有 Runtime、TaskStore、RenderPayload 和安全链；前端下载面与后端权限一致；无需引入前端
  框架、第二套业务路由或新微服务；
- 缺点：需要明确路由、身份存储和迁移；
- 结论：采用。

### 方案 C：独立 SPA + 独立身份/配置服务

- 优点：长期可单独扩容和采用成熟前端工程体系；
- 缺点：当前规模下会提前引入构建链、API 网关、跨服务 Session、部署和观测复杂度，且容易复制权限逻辑；
- 结论：当前拒绝。出现多租户、多个独立 Web 团队或真实扩容证据后再评估。

## 5. 目标信息架构

### 5.1 页面壳层

| 页面 | 目标用户 | 主要能力 | 明确不包含 |
| --- | --- | --- | --- |
| `/login` | Admin、运维人员、待激活用户 | 本地 Admin 登录、飞书登录、首次改密入口 | 任务数据、配置 Secret |
| `/app` | Admin、运维人员 | 小维对话、任务提交、任务列表、当前任务和安全证据 | 系统配置主表单、普通用户门户 |
| `/admin` | Admin | 用户/激活、资源参数、集成、审计和系统状态 | 业务路由、任意 SQL/Policy 编辑器 |
| `/app/tasks/{task_id}` | 已授权主体 | 单任务只读状态和 `RenderPayload` | textarea、提交 JS、配置导航 |
| `/results/{result_ref}` | 该结果申请人/审批人 | 单个数据库结果预览和导出 | 结果列表、任务发起、配置、其他结果导航 |
| `/activation/pending` | 待激活飞书身份 | 安全状态、重试登录提示 | 角色选择、Admin 信息、结果信息 |

路由只是产品契约；实现计划可以在保持兼容的前提下调整前缀，但不能重新合并成一个条件渲染的万能壳。

### 5.2 前端代码边界

- `login`：只处理本地登录、飞书登录和首次改密；
- `workbench`：只处理任务提交、列表和任务轮询；
- `admin`：只处理用户/激活、配置和审计；
- `task-detail`：只读任务投影；
- `result-detail`：只读结果分页/导出；
- 公共模块只放安全的 HTTP、文本渲染、日期和错误映射工具，不放角色或业务判断。

继续使用原生 HTML/CSS/ES module；没有真实复杂度证据前不引入 React/Vue、打包器或组件框架。所有外部文本
继续通过 `textContent` 渲染，禁止 `innerHTML`、内联脚本和 CSP 放宽。

## 6. 统一身份模型

### 6.1 角色与认证来源分离

```text
UserAccount
- user_id                 内部稳定 ID
- actor                   既有任务 actor
- display_name            管理端展示名，不进入授权判断
- role                    ADMIN | OPERATOR | USER
- status                  ACTIVE | DISABLED
- created_at / updated_at

ExternalIdentity
- user_id
- provider                FEISHU
- tenant_id / environment_id
- subject_ref             飞书 open_id；作为受控 PII，不进普通日志
- created_at / last_seen_at

LocalCredential
- user_id                 仅初始化 Admin 使用
- password_hash
- must_change_password
```

角色属于内部账号，`LOCAL_ADMIN`、`FEISHU` 只是认证来源。初始化账号 `admin` 的内部角色是 `ADMIN`；
它可以继续用本地密码登录，也可以在 Admin 发起的受保护绑定流程中增加飞书身份。飞书身份不会因为首次 OAuth
成功而自动获得 Admin。

### 6.2 三角色权限

| 能力 | ADMIN | OPERATOR | USER |
| --- | :---: | :---: | :---: |
| 运维任务工作台 | 是 | 是 | 否 |
| 发起已获授权的任务 | 是 | 是 | 否 |
| 查看本人/当前授权范围的安全任务 | 是 | 是 | 仅具体链接且符合 ACL |
| 查看全部安全任务元数据 | 是 | 否 | 否 |
| 用户与激活管理 | 是 | 否 | 否 |
| 系统与集成配置 | 是 | 否 | 否 |
| 审计私聊/任务内容 | 是，且留审计 | 否 | 否 |
| 数据库真实结果预览/导出 | 仅申请人或审批人 | 仅申请人或审批人 | 仅申请人或审批人 |

前端是否显示按钮只改善体验，后端每个请求都重新执行同一权限判断。`ADMIN` 不是数据库结果万能通行证。

### 6.3 职责名单不是全局角色

下列信息使用独立、封闭的范围绑定，不能继续膨胀全局角色枚举：

- 数据库查询人名单：谁可以对哪个数据库/环境提出查询；
- 数据库审批人名单：谁可以审批哪个数据库/环境的查询，并据此查看该次结果；
- DBA/值班名单：用于通知、运营职责和已定义的 capability policy；
- 群管理员/激活通知人：用于通知，不自动授予查询或结果权限。

这些绑定只能引用已激活的 `UserAccount` 和受信资源 ID；不能携带任意 SQL、工具名或自定义策略表达式。

### 6.4 旧身份标签迁移

| 旧标签 | 新产品角色 | 额外迁移 |
| --- | --- | --- |
| `admin` | `ADMIN` | 保留必要的资源职责绑定 |
| `operator` / `dba` / `oncall` | `OPERATOR` | DBA/值班身份迁入范围名单 |
| `viewer` / `approver` | `USER` | 查看/审批能力迁入具体资源或流程绑定 |

迁移必须可重复、可审计，并在同一 `tenant_id/environment_id` 内拒绝 actor、subject 或本地账号冲突。
静态 JSON 在迁移成功后只读保留一个发布周期，不能和数据库身份目录长期双写。

## 7. 首次激活流程

### 7.1 已登记用户正常登录

```text
用户点击飞书登录
→ 服务端签发一次性 OAuth state
→ 飞书 OAuth 回调取得 open_id
→ 当前 UserDirectory 解析 ExternalIdentity
→ 账号 ACTIVE 且角色允许目标页面
→ 轮换并签发 digest-only Web Session
→ 回到服务端保存的闭集 return intent
```

`return intent` 只能是 `WORKBENCH`、`TASK_DETAIL(task_id)`、`RESULT_DETAIL(result_ref)` 或
`ADMIN_CENTER` 之一，由服务端保存并和一次性 state 绑定；不接受任意 URL，避免 open redirect。

### 7.2 未登记用户从 Web 或结果链接进入

```text
OAuth 回调取得 open_id
→ 查不到 ExternalIdentity
→ 幂等创建或复用 PENDING ActivationRequest
→ 不签发业务 Session
→ 显示“激活申请已提交”
→ Admin 管理中心出现待办，并发送安全通知
→ Admin 明确批准/拒绝
→ 用户重新飞书登录；批准者得到正常 Session
```

`ActivationRequest` 至少包含：内部随机 request ID、tenant/environment、provider、subject_ref、触发来源
（Web/结果/群）、状态、申请/处理时间、处理 Admin 和目标角色。它不保存原始请求正文、数据库 SQL、结果行、
Secret 或任意 return URL。

相同作用域和 subject 只能有一个有效的 `PENDING` 申请；重复 OAuth 不制造待办风暴。状态闭集为
`PENDING / APPROVED / REJECTED / EXPIRED`，所有状态迁移使用事务和 CAS，审批重放不能改变既有结果。

Admin 审批时默认角色为 `USER`；提升为 `OPERATOR` 必须显式选择并可审计。任何 Web/群激活路径都不能
授予 `ADMIN`；新增 Admin 只允许现有 Admin 在管理中心执行独立的高风险操作。

### 7.3 未登记用户在群里 @ 小维

```text
飞书 listener 验证事件与 sender open_id
→ 身份目录无记录
→ 创建/复用 ActivationRequest
→ 返回通用激活卡片：@申请人 + 可识别且在群内的 Admin
→ 卡片只写“需要管理员激活”，附申请人验证链接
→ OAuth 回调所得 open_id 必须与群事件 sender 绑定一致
→ Admin 审批后，申请人重新提交原任务
```

群卡片不得包含原始提问、SQL、数据库名、结果是否存在或 Admin 私人联系方式。群内没有可 @ 的飞书
Admin 时不报错、不泄露目录，只提示“已通知管理员”，同时保留 Admin 中心待办。

### 7.4 审批后的会话和撤权

- 审批只建立账号/外部身份映射，不代替目标资源权限或结果 ACL。
- 禁用账号或撤销身份后，后续受保护请求立即失败；已有 Session 失效或在下一次请求中被拒绝。
- 被拒绝/过期后可以由用户重新申请；旧 request ID 不复活。
- 审批失败不得留下“账号已建、身份未绑”或“身份已绑、角色未建”的半完成状态。
- 为避免激活前请求在事后意外执行，群任务不排队、不自动重放；结果页只能由用户主动重新打开。

## 8. 飞书连接测试与用户登录彻底分开

三条流程使用不同入口、不同 state digest domain 和不同结果语义：

| 流程 | 发起者 | 是否要求身份已登记 | 是否签发 Session | 结果 |
| --- | --- | :---: | :---: | --- |
| 飞书凭据测试 | Admin | 否 | 否 | App ID/Secret 是否可用 |
| 飞书 OAuth 回调测试 | Admin | 否 | 否 | 授权跳转与 code exchange 是否成功 |
| 用户登录/激活 | 任意访问者 | 登录要求是；未知则申请激活 | 已登记且 ACTIVE 才是 | 登录或待激活 |

配置页文案必须写“测试 OAuth 回调（不会登录或绑定用户）”，不能再出现“请先配置 user ID 才能测试”的
产品暗示。当前代码的连接测试语义保持不变；本轮只补清晰的 UI 与激活链，不把正确逻辑改坏。

## 9. 页面与交互设计

### 9.1 登录页

登录页使用独立视觉壳，不再复用工作台的零散表单：

- 左侧（或宽屏背景区）：小维品牌、产品说明、“策略治理的运维任务工作台”；
- 右侧登录卡：`用户名`、`密码`、主按钮“登录”，以及可用时的“使用飞书登录”；
- 首次密码为默认值时，登录后只进入强制改密页；改密完成前不能访问工作台和管理中心；
- 错误只用闭集文案，不区分账号不存在、密码错误、身份未激活等可被枚举的信息；
- 连接状态只显示“系统可用/暂不可用”，不暴露数据库、主机、版本或异常正文；
- 窄屏仍可完成登录和改密。

### 9.2 运维任务工作台

- 入口首页以“小维对话/任务输入”为第一视觉焦点；任务列表和当前任务为辅助区；
- 系统配置从工作台移出，Admin 通过顶部“管理中心”进入；
- `ADMIN` 显示角色标识和管理入口，`OPERATOR` 不看到配置入口；
- 支持 1024px 及以上常见桌面/笔记本宽度，1280/1440 做主要视觉验收；
- 低于桌面下界时给出静态可读提示，不加载手机版任务提交布局；
- 任务结果继续复用 `TaskViewRuntime + RenderPayload`，入口不复制业务路由或证据语义。

### 9.3 Admin 管理中心

左侧一级导航固定为：

1. **概览**：服务可用性、待激活数、待应用配置、最近测试；
2. **用户与权限**：用户、角色、状态、飞书绑定、查询人/审批人/DBA/值班范围；
3. **资源配置**：数据库与 Prometheus；
4. **AI 与飞书**：AI API、飞书应用、OAuth 回调、连接测试；
5. **审计**：配置变化、激活审批、敏感内容查看记录；
6. **系统状态**：加载代次、服务版本、脱敏诊断与需要执行的重启提示。

“清除凭据”“禁用用户”“新增 Admin”等破坏性动作与普通保存分开，要求明确二次确认，不与“测试连接”
并排做成容易误点的同级主按钮。

### 9.4 普通用户结果页

- 未认证时只显示“使用飞书登录查看此结果”；
- 未激活时进入激活申请，不展示结果元数据；
- 已激活但无 ACL 时返回统一不可用页，不区分结果不存在、过期或无权限；
- 授权后只展示本次结果的概要、分页预览、审批与有效期信息，以及符合既有规则的导出入口；
- 不提供“我的结果”、搜索、推荐、任务列表、AI 输入框、侧边栏或 Admin 导航；
- 页面以手机链接打开为主要场景，必须支持窄屏、键盘与屏幕阅读器；
- 浏览器不得缓存真实结果，响应使用 `Cache-Control: no-store`，退出/撤权后清除已渲染数据。

### 9.5 视觉与可用性基线

- 视觉方向采用“冷静、可信、面向运维”的浅色界面：深墨绿作为主色，暖灰作为页面底色，状态色只用于
  成功、等待、警告和失败，不用大面积高饱和渐变；
- 统一 8px 间距体系、12–16px 圆角、清晰的标题层级和 44px 最小点击区；
- 表单使用“标签 + 示例/说明 + 输入 + 就地校验”，不把内部字段名直接暴露给管理员；
- 重要状态同时使用文字、图标和颜色，不能只靠颜色区分；
- 表格在窄桌面改为横向滚动或摘要卡，不通过缩小字号塞满；
- 空状态必须告诉用户下一步，例如“尚无待激活用户”“保存配置后测试连接”，不只显示空白；
- 危险操作使用独立危险区；主按钮每个页面原则上只有一个，避免“保存/测试/清除/发布”同级竞争。

## 10. Admin 参数维护模型

### 10.1 数据库资源

每个资源使用封闭 DTO，不接受任意 JSON：

```text
环境                  test / prod 等受信枚举
显示名称
数据库类型            代码支持的闭集
主机 / 端口
数据库或默认 schema
用户名
密码或 Secret         只写，永不回显
TLS 模式               关闭 / 校验证书等受支持闭集
启用状态
查询人名单
审批人名单
```

稳定 `resource_id` 由系统生成或按严格规则创建，放在高级信息中。页面不能编辑 SQL 模板、SQLGuard、
capability、工具类、任意驱动模块、任意连接参数字典或网络代理。

### 10.2 Prometheus 资源

```text
环境 / 显示名称
服务地址
认证方式              none / basic / bearer 等受支持闭集
用户名                仅 basic
密码或 token          只写
TLS 模式
启用状态
允许使用该资源的运维范围
```

URL 必须经过目标类型、协议、主机和网络策略校验；不能借配置页把任意 URL 变成服务器端请求代理。

### 10.3 AI API

第一版只开放已有 adapter 真正支持的字段：

```text
Provider              代码支持的闭集，初始为 Gemini
启用状态
API Key               只写
模型 ID               由该 adapter 的校验规则限制
API Origin            默认官方；只有 adapter 明确支持时才可配置
```

配置 AI 只改变模型 adapter 的连接参数，不改变模型是否拥有工具权、任务目标、SQL、审批或执行顺序。
新增 Provider 仍需代码、测试和 ADR，不允许在页面填写 Python 类名或动态插件。

### 10.4 飞书

```text
App ID
App Secret            只写
OAuth callback URL    服务端生成、只读、一键复制
消息/登录启用状态
凭据测试
OAuth 回调测试        明确标注“不登录、不绑定用户”
```

真实凭据测试与真实 OAuth 网络调用仍要满足部署环境授权和网络边界；测试结果不保存 Token 或 Provider 原文。

### 10.5 保存、测试和生效

不恢复已被否决的通用配置发布平台。第一版保留最小且诚实的三步：

1. **保存**：服务端校验闭集字段，Secret 缺省表示保留，清除走独立动作；同目录临时文件 + 原子替换；
2. **测试**：Admin 明确点击才发起对应连接探针；测试新配置失败不会把任务结果或 readiness 冒充成功；
3. **应用**：页面区分“已保存”和“服务已加载”。能安全热载的 adapter 可原子换代；不能热载的服务明确列出
   一次应用动作/重启，不挂载 `docker.sock`，不在 Web 内造通用进程管理器。

目标是让管理员不再手工编辑 `.env`/JSON；若第一阶段仍需一次服务重启，Web 必须给出具体服务和状态，不能
只显示抽象 `generation`。配置格式不合法时保留上一份有效配置；不建设历史版本库、任意回滚树或多写者 CAS。

## 11. 数据库结果访问边界

### 11.1 两层证据必须分开

| 内容 | 群成员/安全任务详情 | 申请人/审批人结果页 |
| --- | :---: | :---: |
| 状态、耗时、目标别名、安全摘要 | 是 | 是 |
| “还有更多证据”提示 | 是 | 是 |
| 真实结果行 | 否 | 是 |
| 结果文件/导出 | 否 | 是 |
| SQL 中可能含敏感值的原文 | 否 | 仅既有规则允许时 |

飞书卡片和普通 `RenderPayload` 不嵌入真实结果行。它们只提供受保护的 `/results/{result_ref}` 链接。

### 11.2 后端访问路径

新增窄 `ResultAccessService`，但不复制数据库能力的业务与安全链：

```text
result_ref
→ 当前已认证 principal
→ ResultAccessPort 读取既有结果元数据与 ACL
→ 确认 principal 是 requester 或该次 approver
→ bounded preview / export ticket
→ result-detail shell 安全渲染
```

- `result_ref` 使用不可枚举的随机引用，但随机性不代替认证；
- Web 不能从 TaskStore 或 Evidence 猜测谁是审批人；ACL 的真源必须来自数据库查询结果域；
- 激活只把飞书身份绑定到内部 user/actor，不添加 requester/approver 关系；
- Admin 若不是该次申请人或审批人，结果接口仍返回同样的隐藏式拒绝；
- 导出规则与飞书已确定规则一致，并由服务端生成短时、单用途或受 Session 绑定的下载授权；
- 当前仓库没有该子系统，实现计划必须先定位既有结果真源或定义 adapter，不能拿测试数据冒充接入。

## 12. 后端组件与责任

继续使用模块化单体和窄进程，不新增身份微服务或配置微服务：

| 组件 | 责任 | 禁止 |
| --- | --- | --- |
| `UserDirectory` | 用户、角色、状态与外部身份读取 | 任务执行、结果 ACL 推断 |
| `ActivationStore` | 待激活事实、CAS 审批、去重/过期 | 自动决定角色、保存原始请求 |
| `IdentityActivationService` | 创建申请、审批、绑定、撤权 | 飞书网络、Task/Tool 调用 |
| `WebAuthService` | OAuth state、Session、认证来源 | 自动注册或提权 |
| `IntegrationConfigService` | 类型化配置、Secret 保留/清除、加载状态 | capability/Policy/SQL 编辑 |
| `ResultAccessService` | 结果级 ACL、预览和导出适配 | 复制数据库查询能力 |
| Web/飞书 interfaces | 协议解析、认证上下文、页面/卡片投影 | 业务路由、审批和工具执行 |

`TaskStore` 仍是任务真源，`ChannelStore` 仍只保存渠道绑定/投影，结果域仍是数据库结果真源。身份、渠道、任务、
结果四类事实不互相复制。

## 13. 部署形态

### 13.1 产品部署与离线开发分开

- `dev/offline/CI` 继续默认禁止真实 socket 和外部调用，确保测试不会意外访问飞书、数据库或模型；
- 文档化的 `release` 部署是用户安装路径：启动所有已完成的应用进程；缺少某项配置时，该功能显示“待配置”，
  不能把整个 Web 拉垮；
- 配置齐全并通过必要检查后，已实现功能可用，不再要求用户寻找历史 M/RI feature flag；
- 真实目标、凭据、网络、部署和 canary 的具体执行仍需对应环境的明确授权与证据；本规格不代替该授权。

### 13.2 首次启动

- migration 完成后幂等创建唯一 `admin/admin`，`must_change_password=true`；
- 第一次登录只能改密、退出，改密撤销旧 Session；
- 项目负责人接受发布地址在改密前即可访问的风险，不强制 loopback 首启；部署文档必须醒目标注默认凭据和
  “部署后立即改密”；
- 安全底线不因该取舍放宽：密码哈希、Session、Origin/CSRF/CSP、Cookie、速率限制和审计继续生效；
- 正式跨主机/公网部署使用 HTTPS。局域网 HTTP 是受信网络模式，不开放内部 API、PostgreSQL 或 worker 端口。

### 13.3 服务可用性

- Web 核心 readiness 只依赖数据库、migration、认证存储和自身装配；第三方 Provider 故障不让管理页不可用；
- listener/worker 在功能已启用但配置缺失时进入可观测的 `waiting_for_config`，不忙循环、不反复刷外部请求；
- 任务 Worker 是唯一拥有完整 Runtime/Runner/Gateway/目标 adapter 的进程；Web、飞书 listener、渠道 worker
  继续使用窄装配；
- release Compose 只发布 Web 所需端口；内部 API、数据库、worker 管理口不暴露到宿主外网。

## 14. 错误、隐私与审计

### 14.1 用户可见错误

闭集区分：

- 登录失败；
- 身份待激活；
- 账号已停用；
- 结果不可用；
- Provider 未配置/待应用/测试失败；
- 服务暂不可用。

普通用户不能通过错误差异判断某个结果、用户、群或资源是否存在。Provider 原始正文、数据库异常、Token、
Secret、digest 和内部地址不进入页面。

### 14.2 Admin 审计

下列动作写入结构化审计：

- 激活批准/拒绝、角色改变、账号禁用/启用；
- 查询人/审批人/DBA/值班范围改变；
- 配置保存、Secret 替换/清除、连接测试；
- 查看私人聊天或敏感任务正文；
- 结果导出（沿用结果域审计）。

审计只保存必要引用、操作者、时间、动作和闭集结果；不复制 Secret、真实结果行或 Provider 原始响应。

## 15. 安全不变量

1. LLM 不参与用户激活、角色分配、结果 ACL、配置发布、Secret 选择或审批裁决。
2. Web/飞书仍是薄入口；任务继续走统一 Runtime、安全链和 TaskStore。
3. 链接、OAuth 成功、群成员身份、Admin 角色和激活批准都不能单独授予数据库结果权限。
4. OAuth 登录、激活和连接测试使用隔离的 state 语义；测试永不签发用户 Session。
5. 所有 Session/state/一次性票据只在浏览器保存原文，服务端保存 digest 与必要时效事实。
6. Secret 只写不回显，不进环境明文、日志、trace、异常、DOM、测试夹具和 Git。
7. 自定义 endpoint 必须由对应 adapter 明确支持并通过 SSRF/协议/host 边界；不能提供任意 URL 探测器。
8. 禁用/撤权在后续请求实时生效；页面必须删除已渲染的受保护数据。
9. Admin 管理权不能绕过 SQLGuard、ToolPolicy、ApprovalGate、ToolGateway 或终态保护。
10. release 可用性不反向削弱 offline/CI 的 `--disable-socket` 和真实调用证据门。

## 16. 验证与验收设计

### 16.1 单元/契约测试

- 三角色与职责名单矩阵的正反例；
- 旧标签迁移、重复 actor/open_id、跨租户/环境冲突；
- 激活申请去重、过期、拒绝、并发审批、重放和半事务失败；
- 群事件 sender 与 OAuth 返回 open_id 不一致时拒绝；
- `return intent` 闭集与外部 URL/路径穿越反例；
- 飞书连接测试不访问身份目录、不签 Session、不创建激活申请；
- 本地 Admin 首次改密前的路由闭集；
- 配置字段、Secret 保留/替换/清除、SSRF、跨环境和原子写失败；
- Admin/运维/普通用户下载到的 shell 与 JS 闭集；
- 数据库结果 requester/approver 正例，以及 Admin、群成员、其他普通用户反例；
- 禁用/撤权后清除页面内容，错误不泄露结果存在性。

### 16.2 安全测试

- CSRF、Origin、Cookie、Session rotation、OAuth login CSRF/replay/expiry；
- 激活链接猜测、重复审批、跨群/跨 tenant/跨 environment 绑定；
- 角色前端篡改、隐藏按钮直调 API、Admin 结果越权；
- 外部文本 XSS、CSP、无 `innerHTML`/内联脚本；
- Secret-shaped literal、日志/异常/审计脱敏；
- 配置 endpoint 的 DNS/IP/重定向 SSRF 反例；
- Web/飞书进程继续不加载完整 Runtime/Gateway/目标 adapter。

### 16.3 集成与浏览器验收

- PostgreSQL 上身份/激活 CAS、Session 撤销和迁移一致性；
- fake 飞书 OAuth 的已登记登录、未知身份激活、Admin 审批、重登闭环；
- 数据库结果链接的分页、撤权和导出授权闭环；
- 1024/1280/1440 工作台与管理中心视觉检查；
- 手机宽度的登录、激活、任务详情和结果页视觉/键盘检查；
- wheel/容器内静态资源完整性；
- release Compose 中所有已实现进程启动、缺配置等待、配置后可用、内部端口不暴露。

### 16.4 证据分级

- 代码/测试通过只证明离线实现；
- 浏览器截图只证明指定尺寸的 UI 检查；
- 真实飞书、数据库、Prometheus、AI API 必须分别留下部署 SHA、配置版本、脱敏 trace 与用户验收；
- 任一真实集成未验证时，必须写“未覆盖”，不能用 fake 或 CI 代替。

## 17. 实施拆分边界

本规格是一个产品目标，但实现必须拆成可独立评审、可回滚的阶段；不能以一个巨型 PR 落地：

1. **W0 文档与 ADR**：修订 ADR-014/015 及身份、配置、结果边界；不写源码；
2. **W1 用户目录与激活内核**：三角色、持久身份、激活申请、迁移与 application 服务；
3. **W2 登录与页面壳**：美化登录/改密，拆分工作台和 Admin 壳；
4. **W3 用户与权限管理**：激活审批、角色、职责名单和审计；
5. **W4 资源与集成配置**：数据库、Prometheus、AI、飞书参数与连接测试；
6. **W5 单结果查看**：对接真实结果真源与既有 ACL，完成预览/导出；
7. **W6 产品部署**：release profile、服务等待配置、浏览器视觉与真实集成分阶段验证。

每个阶段都从最新 `main` 开独立分支，先计划和测试再实现；涉及真实 Provider、目标、Secret、部署和 canary
时仍单独取得授权。W1–W4 不得因为 W5 尚未实现而伪造数据库结果页面。

## 18. 明确非目标

- 普通用户首页、“我的结果”、普通用户任务列表或 AI 工作台；
- 手机端运维工作台、任务发起、任务列表和后台配置；
- 任意 RBAC/Policy DSL、用户自定义角色、组织同步或多租户管理平台；
- 让 Admin 页面编辑 capability、Planner、SQL/PromQL 模板、ToolPolicy、ApprovalGate 或工具顺序；
- 引入 SPA 框架、微前端、身份微服务、配置微服务、消息总线或 Docker Socket 管理；
- 通用动态 Provider 插件、任意 Python/URL/驱动配置；
- 配置历史版本平台、自动回滚树、多写者配置协同；
- 自动执行激活前请求、自动批准身份、首个 OAuth 用户自动成为 Admin；
- 以 Admin 角色绕过数据库结果 ACL；
- 在本设计中开放新的 E1、生产写、真实调用、部署或用户验收权限。

## 19. 对既有规范的影响

规格获批后、写实施计划前，至少需要成套修订：

- `ADR-014`：放开持久化用户目录、激活 state/context、飞书 Admin 配置权和第三类用户来源；
- `ADR-015`：从双 Provider 本地配置扩展到受控 AI/资源配置，同时保留 Secret 与网络边界；
- `ADR-013`：只补充结果深链与身份目录演进，不能改变薄渠道、TaskStore/ChannelStore 真源和进程隔离；
- `ARCHITECTURE.md`：统一用户/角色/职责、结果访问和 release 部署边界；
- `DEVELOPMENT_PLAN.md`：为 W0–W6 建立里程碑顺序和真实集成门；
- `README.md`：更新登录、初始化、Admin 配置和产品部署路径；
- `AGENT_HANDOFF.md`：只记录实际合入、测试、部署与未覆盖证据。

这些修订必须明确替代 RI5 中“仅本地 Admin、仅 Gemini/飞书、首次必须 loopback 改密”的旧产品范围；
不允许一边保留旧限制，一边在源码里偷偷扩大权限。
